# TARA — deployable static site

This directory is the whole TARA learning system as a **static site**: an app shell
plus 76 individually-fetched, gzip-compressed payloads. It is the same application as
`../app/tara-app.html` (the 2.99 MB single-file artifact build), split so that a first
visit downloads ~80 KB gzipped instead of 2.85 MB, and each section's content arrives
on demand and is then cached by the browser and by a service worker.

Nothing under `../app/` is modified. This directory is generated by `build-site.js`,
which reads the same sources the artifact build reads.

```
open index.html over http(s)   →   #today, exactly as before
```

---

## Layout

```
site/
  index.html                 the shell: document wrapper, chrome, inline payload manifest
  css/shell.<hash>.css       shell.css + frames.css + cases.css + drill.css, concatenated
  js/app.<hash>.js           shell.js, today.js, search.js, review.js + the 8 section modules
  assets/<name>.<hash>.gz    76 payloads, each `gzip -9` of one source file
  manifest.json              web app manifest
  sw.js                      service worker (generated from tools/sw.tpl.js)
  icons/                     icon-192, icon-512, both maskable variants, icon.svg
  .nojekyll                  belt and braces; Pages' artifact upload does not run Jekyll
  .github/workflows/pages.yml  deploy-on-push workflow (no build step runs on GitHub)
  build-site.js              the generator — run it to rebuild everything above
  tools/                     png.js (PNG encoder), icons.js (the mark), sw.tpl.js
  README.md  REPORT.md
```

Every URL in the site is **relative**. There is not one leading-slash path anywhere,
so the site works both at an origin root and under a subpath such as
`https://<owner>.github.io/<repo>/`. Both were verified — see `REPORT.md`.

## Rebuilding

```
node /mnt/project-files/site/build-site.js
```

Node ≥ 18, no dependencies, no network. It:

1. `require`s `../app/payloads/{core,frames,data}.js` with the same `ctx` object
   `../app/build.js` builds, so the collectors produce exactly the same 76 entries.
2. Encodes each entry with `../app/lib/payload.js` (`gzip -9`, unchanged), and writes
   the **raw gzip bytes** to `assets/<safe-key>.<sha256-10>.gz`. Every one of the 76
   files is byte-identical to the corresponding base64 payload embedded in
   `../app/tara-app.html` — that equivalence is asserted in `REPORT.md`.
3. Concatenates the CSS and JS in the same order `build.js` uses (shell first), with
   each JS module in its own IIFE, and writes them to content-hashed filenames.
4. Wraps the shell fragment (`../app/src/shell/index.tpl.html` has no doctype, `<html>`,
   `<head>` or `<body>` — the artifact publisher supplied those) in a real HTML document
   with charset, viewport, theme-color, manifest link and apple-touch-icon, plus the
   same small CSS reset the artifact runtime injected, so rendering is unchanged.
5. Inlines `window.__MANIFEST` (76 × `{key, section, kind, raw, enc, gz, file}`, ~8 KB)
   so the first route needs no extra round trip to find its payload.
6. Generates the icons and `manifest.json`, taking `theme_color` and `background_color`
   from the app's own `--accent` and `--paper` tokens read out of `shell.css`.
7. Generates `sw.js` from `tools/sw.tpl.js` with a cache version hashed over every
   shell byte.

### The one change to the application code

`build-site.js` replaces exactly one block in `shell.js` — `APP.payload` /
`APP.payloadJSON` / `APP.hasPayload` — so that a payload is fetched over HTTP instead
of being read out of an inert `<script type="text/plain">` tag. The decode path is
unchanged: the `.gz` bytes go through the same `DecompressionStream('gzip')`.

```js
const res = await fetch(new URL(rec.file, document.baseURI));
let bytes = new Uint8Array(await res.arrayBuffer());
if (bytes[0] === 0x1f && bytes[1] === 0x8b) {           // a plain host serves the container intact
  const stream = new Blob([bytes]).stream().pipeThrough(new DecompressionStream('gzip'));
  return await new Response(stream).text();
}
return new TextDecoder('utf-8').decode(bytes);           // a host that set Content-Encoding already inflated it
```

The magic-number check is what makes the `.gz` extension safe on *any* static host: a
host that serves `.gz` with `Content-Encoding: gzip` has the browser inflate it, and
the fallback handles that without a second code path. If an inline `P:<key>` tag is
present the old path still works, so a single-file build of the same sources runs here
unchanged.

The substitution is anchored on the exact source text. If `shell.js` ever changes shape
the build **fails loudly** rather than silently shipping the DOM-reading version.

Everything else — the router and its legacy redirects, the tier control and its
scroll-anchoring logic in `sections/packs.js`, the LRU of four `srcdoc` iframes with
**no `sandbox` attribute**, `window.APP` and its public methods, `localStorage["tara.tier"]`
with `tara.resolution` as an alias, the no-reorder rule — is copied through untouched.

### Reproducibility

Two consecutive builds produce byte-identical `index.html`, CSS, JS, `manifest.json`,
`sw.js` and all 76 `assets/*.gz`. The five image files under `icons/` are the exception
**in this container only**: the encoder output is deterministic (verified: 1,393 B for
the 192 px PNG on every run), but the filesystem here rewrites image files on write to
attach C2PA content-credential metadata carrying a fresh UUID. The cache version is
therefore hashed over the icons *as the encoder produced them*, not as they landed on
disk, so `sw.js` stays deterministic too.

## Progressive web app

* `manifest.json` — name/short_name "TARA", `start_url` `./#today`, `scope` `./`,
  `display` `standalone`, `theme_color` `#1f3fb8` (`--accent`), `background_color`
  `#fbfaf7` (`--paper`), five icons.
* `sw.js` — precaches the shell on install (index.html, the hashed CSS and JS,
  `manifest.json`, all five icons) and caches `assets/*.gz` on first use.
  * navigations and `index.html`: **network-first**, falling back to the cached shell,
    so a redeploy lands immediately and the app still opens offline.
  * `assets/`, `icons/`, hashed `css/` and `js/`: **cache-first** — the filename changes
    when the bytes do, so a hit is always correct.
  * **cross-origin requests are not intercepted at all.** The packs and demos pull
    highlight.js and three.js from cdnjs/jsDelivr, web fonts from
    `fonts.googleapis.com`, and the sprint pulls Pyodide from jsDelivr. Those are
    third-party, versioned and large; the browser's own HTTP cache handles them, and a
    genuine failure must stay visible rather than be masked by the worker.
  * `CACHE_VERSION` is regenerated on every build; `activate` deletes any older
    `tara-shell-*` / `tara-assets-*` cache and claims open clients.
* Registration happens **only** when `location.protocol === 'https:'` or the host is
  `localhost` / `127.0.0.1` / `[::1]`. Never from `file://`, never from an artifact frame.

## The Python runner in the crash sprint

The 7-day sprint runs numpy and real einops through Pyodide 0.28.3. It was disabled in
the artifact only because the artifact CSP allows no `connect-src` host at all, so
`loadPyodide()` could not fetch its wasm. On a real https origin nothing blocks it, and
the existing machinery already does the right thing:

* Pyodide is loaded **lazily and only inside the sprint frame** — the frame exists only
  on `#sprint`, and inside it `bootPyodide()` fires on the first pointer/key event
  (`src/sprint.html`, "boot on first real interaction, not on page load"). The shell
  never touches the CDN.
* When the sprint frame opens it probes `connect-src` once with a small GET to the
  Pyodide index. If that is refused, `APP.sprintPyBlocked()` shows the plain
  "Python exercises cannot run here" notice above the frame — the graceful fallback,
  kept exactly as it was.
* einops installs from a base64 wheel embedded in `src/sprint.html`, so only Pyodide
  itself needs the network.

Exercises are unchanged. See `REPORT.md` for exactly what was and was not verified here.

## Deploying

`.github/workflows/pages.yml` deploys this directory to GitHub Pages on push to the
default branch using `actions/configure-pages`, `actions/upload-pages-artifact` and
`actions/deploy-pages`, with `pages: write` + `id-token: write` and a `pages`
concurrency group. **No build step runs on GitHub** — the committed files ship as they
are. If the repository keeps the site in a subdirectory, point the workflow's
`upload-pages-artifact` `path:` at that subdirectory; if the default branch is not
`main`, change the `on.push.branches` entry.

`build-site.js` and `tools/` are committed and therefore uploaded with the site. They
are a few KB of text, they make the split reproducible, and nothing serves them.

## Requirements

`DecompressionStream('gzip')` — Chrome 80+, Safari 16.4+, Firefox 113+. Without it the
shell renders one line saying so and stops, exactly as the single-file build does.
